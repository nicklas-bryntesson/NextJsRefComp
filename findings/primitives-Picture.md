# findings/primitives-Picture.md

`TagHelpers/PictureTagHelper.cs` (`app-picture`) and the `MediaHelper` static
behind it, ported to `web/src/primitives/Picture/` in three ordered steps.
Step 1's files landed in `474f53a` (see F-NEW on the shared tree); step 2 is
`072dbfa`, step 3 is `5c05a3e`.

Route: `/primitives/picture`. Probes: `web/tasks/probes/picture-{guard,negotiate,
cls,axe,reflow,computed}.cjs`, plus `gen-media.cjs` which generates the fixture
set and two throwaway diagnostics (`picture-sizes-diag.cjs`,
`picture-live-diag.cjs`). Baselines: `web/tasks/snapshots/picture-step1.json`,
`picture-step2-before-tailwind.json`.

**Offline by construction.** Umbraco media is a remote host that is unknown at
port time, so the route renders **local files under `web/public/media/`** — 63
real images, generated by `gen-media.cjs` at the exact widths and aspect ratios
the presets ask for, in all three formats the source negotiates over. Real files
at real sizes rather than one placeholder repeated, because the whole CLS
question is *when the browser learns the aspect ratio* and identical candidates
would have made the port measure better than the source behaves.

## The headline: `next/image` is the wrong tool here, and Next's own linter says so

### F-NEW · `MediaHelper` is not thin, and three of its four guarantees are inexpressible in `next/image`

**Surface:** `TagHelpers/MediaHelper.cs` (6.9 KB) vs `next/image`. **The decision
this port was commissioned to make.**

The owner's expectation was "port the markup faithfully unless `MediaHelper`
turns out to be thin". It is not thin. It is a preset table plus two distinct
negotiation modes plus a format ladder, and the contract it guarantees is:

| # | Guarantee | `next/image` |
|---|---|---|
| 1 | Declarative **format negotiation** — three `<source>`s per breakpoint, `image/avif` → `image/webp` → untyped floor; the browser picks the first it can decode | **Changed.** Negotiates server-side from the `Accept` header on `/_next/image`. Fewer bytes of markup, but the choice moves from client to server and requires routing every image through Next's optimiser |
| 2 | **Resolution switching** — `srcset` widths + `sizes` | **Kept**, but the widths are not yours: they snap to `deviceSizes`/`imageSizes`, which are app-global in `next.config.ts`, not per-preset |
| 3 | **HTML art direction** — `<source media>` selecting a *different Umbraco crop* per breakpoint. `hero` runs `mobile` 4:5 → `portrait` 3:4 → `mid` 16:9 → `wide` 21:9 | **Cannot express.** `next/image` renders a bare `<img>`. No `<picture>`, no `<source media>`. This is not one image at four sizes, it is four different crops |
| 4 | **Container-query-driven** source selection — `teaser` renders two whole `<picture>`s and the consumer hides one with a container query | **Cannot express**, and neither can `<picture media>`; see F-NEW below |
| 5 | **Named crops with focal point** — `GetCropUrl(cropAlias, width, preferFocalPoint: true)`; the rectangle is editor-controlled | **Cannot express.** The loader takes a URL and a width and does not model crops |
| 6 | Zero client JavaScript | Kept (`next/image` output is markup too) |

**On (5) there is no escape route that leaves anything behind.** Passing the
already-cropped Umbraco URL as `src` makes `/_next/image` re-optimise an
already-optimised image — a second transcode, a second cache, a second bill. A
custom loader avoids that, but a custom loader bypasses `/_next/image` entirely,
which means giving up (1) and the whole optimiser; what remains is an `<img>`
with a `srcset` you compute yourself, i.e. **strictly less than the source
already has, minus `<picture>`.**

**And `images.remotePatterns` cannot be configured at all here**, which is the
concrete blocker the brief asked about. The Umbraco media host is a CMS
deployment detail; `next/image` throws at *runtime* on an unconfigured hostname
("hostname is not configured under images in your next.config.js"). The two
escapes — `images.unoptimized: true` or a custom loader — each remove the reason
to use it. `web/next.config.ts` needs **no change**, which is the useful
practical answer.

**The corroboration is inside Next itself.** `@next/eslint-plugin-next`'s
`no-img-element` — the rule whose entire purpose is to push you towards
`next/image` — opens with:

```js
if (node.parent?.parent?.openingElement?.name?.name === 'picture') {
  return;
}
```

Measured: `npm run lint` reports nothing for `MediaFigure.tsx`'s `<img>`, and a
speculative `eslint-disable-next-line` on it was flagged as an *unused* directive.
**Next's own tooling concedes the `<picture>` case**, because `next/image` cannot
do art direction. That is not an argument I constructed; it is the framework
agreeing from its own side.

> One consequence of the exemption worth knowing: it is **lexical**, reading the
> immediate JSX parent. Extracting the `<img>` into its own component makes the
> rule fire on markup that is still inside a `<picture>` at runtime — a false
> positive that punishes a normal refactor. `MediaFigure.tsx` keeps the `<img>`
> inlined for that reason and says so.

**Decision: port the markup faithfully. `next/image` is not deferred to a later
step, it is declined.** Guarantee (3) alone disqualifies it, and (4) and (5)
independently confirm it. The one thing `next/image` does that the source does
not — **require `width`/`height`** — is a genuine improvement and was adopted
*without* it, in step 2. See the CLS entries.

**Not an Open question, with one exception.** A hypothetical future preset that
is pure resolution switching over a single crop with no focal point would be
expressible through `next/image`, and would then get its optimiser for free.
Neither of the two presets is that, and mixing two image pipelines in one app to
serve one hypothetical preset is worse than the duplication it saves.

### F-NEW · The `teaser` preset always downloads two images and uses one, and `display: none` does not help

**Surface:** `MediaHelper.Presets["teaser"]` + `Teaser.css`. Measured on
`/primitives/picture` with a cold cache.

`teaser` is two complete `<picture>` elements — `StackedSources` (3:2) and
`HorizontalSources` (1:1) — and `Media.css` says outright that visibility "is
controlled by the consuming component (e.g. Teaser.css) via container queries.
Neither class carries display rules here." So the obvious question is whether the
hidden one costs anything.

Measured (`picture-negotiate.cjs`, cache disabled, element scrolled into view so
lazy-loading is not what suppresses the fetch):

| Condition | Files fetched |
|---|---|
| both visible | 2 — `horizontal-320.avif`, `stacked-800.avif` |
| `StackedSources` `display: none` | **2** — both |
| `HorizontalSources` `display: none` | **2** — both |

`display: none` does not prevent an image load in Chromium. **So every teaser
costs two crops and renders one**, and on a twelve-card listing page that is
twelve wasted requests.

**This is a real engineering trade and it is undocumented.** A single `<picture>`
with `<source media>` downloads exactly **one** candidate — that is the whole
point of the element. The source uses two pictures for `teaser` because `<source
media>` only accepts *media* queries, and Teaser's layout switches on its
**container** at 25rem, not on the viewport. Container-query responsiveness is
worth paying for; it just costs 2× image bytes and nothing says so.

It is also the sharpest form of the `next/image` argument: neither `<source
media>` nor `next/image` can respond to a container, so this cost is not
something a different image component would fix.

**Open question for the project owner:** `content-visibility: hidden` on the
inactive picture would suppress the load and is a one-line change in
`Teaser.css`. It belongs to the Teaser port, not this one, so it is recorded
rather than done.

## The `sizes` attribute is the guarantee that breaks, and it breaks in both directions

### F-NEW · `sizes="100%"` is not valid CSS-sizes syntax, silently falls back to `100vw`, and over-fetches by up to 3.3×

**Surface:** `MediaHelper.Presets["teaser"]`, `StackedSources`. Measured at a
1440 px viewport with `deviceScaleFactor: 1`.

The `sizes` grammar is `<source-size-value> = <length> | auto`. A **percentage is
not a length in this context** — there is no reference box for it to resolve
against — so `sizes="100%"` is invalid, is dropped, and the browser uses its
`100vw` default.

Measured rather than quoted. `naturalWidth` on a srcset-selected image is
*density-corrected*, so it reports the slot the browser computed:

| Demo | element box | slot the browser used | candidate fetched |
|---|---|---|---|
| `picture-teaser` (26rem box) | 416 px | **1440 px** (= `100vw`) | `stacked-800` — **2× too big** |
| `picture-classes-default` (15rem box) | 240 px | **1440 px** | `stacked-800` — **3.3× too big** |

If `100%` were honoured the slot would have been 416 px and 240 px and the
browser would have taken `stacked-400`. It reads the viewport instead. **The one
attribute whose entire job is to prevent over-fetching is inert**, and it fails
silently — no console warning, no build error, nothing.

**Decision:** reproduced verbatim in all three steps. Fixing it needs a real
length and the correct length is a property of the *consumer's* layout, which is
exactly the problem the next entry describes. Recorded as an upstream bug.

**Upstream fix:** `sizes="100vw"` states the current behaviour honestly, or
`sizes="auto"` (with `loading="lazy"`, which `teaser` already has) lets the
browser use the element's real laid-out width — which is what `100%` was reaching
for and the only form that actually delivers it.

---

### F-NEW · `sizes="12rem"` under-fetches by 7.4×, because a preset cannot know its consumer's layout

**Surface:** `MediaHelper.Presets["teaser"]`, `HorizontalSources`.

The counterpart failure, same table, opposite direction. `12rem` is not arbitrary
— it is exactly Teaser.css's `--_minMediaSize: 12rem`, the **minimum** of the
media column in `grid-template-columns: minmax(var(--_minMediaSize), 1fr) 2fr`.
So it is correct for one consumer at one container width and wrong everywhere
else.

Measured: slot 192 px (= 12rem) in every case, so `horizontal-320` is always
chosen. In a 1424 px-wide container that is a **320 px file scaled to 1424 px, a
7.4× upscale.** In the 15rem demo the box is 240 px and the slot is 192 px, which
is where the value came from and the only place it is right.

Hero has the same shape of problem in a milder form: `sizes="60vw"` on the `wide`
source assumes the hero occupies 60 % of the viewport, which is true of
`grid-container-full` in the real site and not of an arbitrary consumer.

**The generalisable point, and it is the most transferable thing in this port:**
`srcset` is a fact about the image and `sizes` is a **promise about the
consumer's layout**. `MediaHelper` centralises both in one preset table, which is
right for `srcset` and structurally impossible for `sizes` — the builder cannot
see the box. Nothing in the source or the port can verify it: it is not style, so
no computed-style snapshot sees it; not semantics, so axe does not; not a
dimension, so no reflow or CLS probe does. **`picture-negotiate.cjs` exists
because this class of defect has no other instrument.**

**Decision:** reproduced verbatim. **Open question:** `sizes="auto"` moves the
promise from the preset to the browser and is the only mechanism that can be
right for every consumer. It requires `loading="lazy"`, which `teaser` has and
`hero` deliberately does not — so `hero` genuinely needs a hand-written `sizes`
and `teaser` genuinely does not.

## CLS: the naive measurement said GOOD, and it was wrong

### F-NEW · Step 1 measured CLS 0.253 (POOR) — and three of four network conditions hid it

**Surface:** the step-1 build. `picture-cls.cjs`.

`MediaHelper` emits no `width`, no `height` and no `aspect-ratio`, on any image,
in either mode. This is the layout-shift form of PORTING.md's 300×150 SVG warning
that the Button port hit for real.

| Condition | CLS | Verdict |
|---|---|---|
| local (no throttling) | 0.000 | GOOD |
| fast-4g (40 ms RTT) | 0.000 | GOOD |
| slow-4g (300 ms RTT, 400 Kbps) | 0.000 | GOOD |
| **image-lag** (900 ms on `/media/**` only) | **0.253** | **POOR** |

**Why the first three lie, which is the finding.** Uniform throttling slows the
render-blocking CSS *and* the images together, so the 55 KB Tailwind chunk
arrives last and first paint is deferred until after the hero has decoded. **The
stylesheet accidentally shields the page from its own layout shift.** The shift
is not absent; it is outrun. Reporting "CLS 0.000 on slow-4g, no problem found"
would have been a confident, well-measured, false conclusion.

**And image-lag is not the exotic case, it is the normal one.** Every URL
`MediaHelper` emits is unique per crop × width × format, so a cold ImageSharp
cache makes each of the hero's twelve candidates a first-request server-side
resize. Images being slower than CSS is the *default* state of an Umbraco media
pipeline.

**A CLS number alone is still not sufficient**, because CLS only counts shifts
inside the viewport and half this route is lazy and below the fold. So the probe
also measures the mechanism deterministically — load with every media response
aborted, record each picture's height, load normally, record again:

| | step 1 | step 2 |
|---|---|---|
| unreserved height, 23 pictures | **3998 px** | **0 px** |
| images with `width`+`height` | **0 / 23** | 23 / 23 |
| images with a CSS `aspect-ratio` | **0 / 23** | 23 / 23 |
| worst CLS, any condition | **0.253** | **0.000** |

That second half is a property of the markup — independent of timing, cache and
viewport — and it is what makes the claim checkable.

**Decision:** measured and left alone in step 1 (faithful), repaired in step 2.
Same sequencing as the Button port's `aspect-ratio: auto 1 / 1` icon repair, and
the same class of defect: a replaced element with no intrinsic dimensions.

### F-NEW · The reservation belongs on `<source>`, not on `<img>` — and that is precisely what `next/image` cannot do

**Surface:** step 2, `mediaHelper.ts` + `MediaFigure.tsx`.

The obvious fix is `width`/`height` on the `<img>`. For `hero` it is **worse than
nothing at three of four viewports**, because the crop changes per breakpoint:

| source | media | crop ratio | reserved box |
|---|---|---|---|
| `mobile` | `(max-width: 21.24999rem)` | 4:5 | 380 × 475 |
| `portrait` | `(max-width: 48rem)` | 3:4 | 440 × 587 |
| `mid` | `(max-width: 64rem)` | 16:9 | 740 × 416 |
| `wide` | `(min-width: 64rem)` | 21:9 | 1280 × 549 |

Four genuinely different ratios (pinned in `mediaHelper.test.ts`). The `<img>`'s
`src` comes from `lastSource.widths[0]` = `wide` @1280, so a single pair on the
`<img>` declares 21:9 — and at 320 px the displayed crop is 4:5. The browser
would reserve a letterbox and then reflow to a portrait. **A "just add width and
height" fix would have replaced one shift with a bigger one.**

HTML's answer is `width`/`height` **on each `<source>` inside `<picture>`**. Step
2 emits both: per-source dimensions for the art-direction ladder, plus a
`width`/`height` floor on the `<img>` from the last source's crop for the case
where no `<source>` matches.

Measured, 1280 px: the matched source is `image/avif (min-width: 64rem)
1280×549`, computed `aspect-ratio: auto 1280 / 549`, and the box is
830 × 356 whether the image is loaded or aborted.

**This sharpens the `next/image` verdict rather than softening it.** `next/image`
requires `width`/`height` — one pair, on one `<img>`. For a resolution-switching
preset that is enough. For an art-directed one it is the wrong answer expressed
confidently, and there is no `next/image` API that says "this breakpoint has this
shape".

**Upstream this needs no new CMS data, and that is the actionable part.**
`GetCropUrl(cropAlias, width, …)` resolves the named crop, and an Umbraco crop
definition carries its own width and height. `MediaHelper` already knows every
ratio implicitly — it passes a width and lets the height follow — and simply
throws it away. Emitting `width`/`height` on every `<source>` and the `<img>` is
a local change to `RenderPictureGroup` with no schema change, no editor work and
no new dependency. **This is the port's principal upstream recommendation.**

**Open question:** the port has to *declare* the five ratios it cannot know
(`SourceDefinition.aspectRatio`, optional, absent = no reservation so it is never
a guess). Only `horizontal` 1:1 is evidenced by the source — Teaser.css states
it. The other five are the ratios the fixture set is generated at. Upstream they
must come from the crop definitions; here they are a documented assumption.

## Accessibility: axe is green and cannot see the actual defect

### F-NEW · `Alt ?? ""` makes "decorative on purpose" and "the author forgot" byte-identical

**Surface:** `PictureTagHelper.Alt` (`string?`) → `BuildFigureHtml(altText: Alt ??
"")`. **The port's principal accessibility finding, and the one the
atomica11y criteria were written for.**

The source has three cases and can represent two:

| Author wrote | Emitted | Screen reader |
|---|---|---|
| `alt="Concrete lattice…"` | `alt="Concrete lattice…"` | announced, role image |
| `alt=""` | `alt=""` | **skipped** |
| *nothing* | **`alt=""`** | **skipped** |

Measured on the route — `picture-alt-decorative` and `picture-alt-omitted` render
**identical markup**. And the source's own kitchensink omits `alt` in
`_Components.cshtml`, so the pattern is live.

**Against `docs/atomica11y/main/{informative-image,decorative-image-icon}.md`:**

- `decorative-image-icon` asks that the image be "skipped and ignored" and
  "ignored" by a screen reader. **Met** for `alt=""` — 4 of 23 images on the
  route, verified in the axe census.
- `informative-image` asks that "the content of the image alt text is clear" and
  that "it identifies its role as an image or graphic". **Met** for the 19 with
  non-empty alt. Both criteria are satisfiable by this markup and both are
  satisfied.
- **But the criteria are stated per-image and assume the author's intent is
  known.** Neither can be evaluated for a *forgotten* alt, because the emitted
  markup is a valid decorative declaration. atomica11y's test procedure is
  manual and human — "I HEAR the image is ignored" — and a human running it on a
  forgotten alt hears exactly the pass condition.

**axe cannot help and it is not axe's fault.** `image-alt` checks that an image
has an accessible name *or* declares itself decorative. Measured: **0 violations
in both appearances, both before and after.** So `picture-axe.cjs` prints an alt
census alongside the audit — informative / decorative / no-attribute / broken —
because a green `image-alt` here means "every image declares an intent", not
"every image declares the *right* intent".

**A worse instance is in production.** `_CoverComposition.cshtml`:

```razor
<div class="media-container" role="presentation">
    <app-picture image="@image" preset="hero" alt="@Model.Title" loading="eager" />
</div>
...
<app-heading element="@headingLevel" variant="display" size="1" text="@Model.Title" />
```

The hero image's alt is **the page title, verbatim**, and the same string is
rendered as the adjacent `<h1>`. A screen reader announces the title twice, once
as a graphic. That is not a clear alt in `informative-image`'s sense — it is
noise, and for a decorative backdrop behind its own title `alt=""` is the correct
answer. The `role="presentation"` on the wrapper `<div>` suggests someone already
felt the tension and put it on the wrong element (it does nothing on a `div`
whose child image carries a real name).

**Decision:** reproduced faithfully. `alt` stays optional and `alt ?? ""` stays,
because making `alt` required is an API change that breaks every existing call
site — the decision belongs to the project owner, not the porter.

**Open question, with the React-specific option spelled out.** TypeScript can
express what C# nullable reference types cannot cheaply: a discriminated union
that makes the intent mandatory and unambiguous —

```ts
type Alt = { alt: string } | { decorative: true };
```

— so `<Picture image={x} preset="teaser" />` fails to compile and the author has
to say which they meant. That is a **strict improvement in the port's expressive
power over the source**, achievable at zero runtime cost, and it is the single
highest-value change available to this component. Not taken unilaterally because
it changes the public API.

### F-NEW · The `teaser` preset announces its image twice outside a Teaser, and the source's own demo page does that

**Surface:** `Presets["teaser"]` + `Media.css`'s own comment.

`teaser` renders two `<picture>`s with the **same alt text**. Inside a Teaser one
is `display: none` and therefore out of the accessibility tree, so it is fine.
Outside one, nothing hides either: both are visible and both are announced.

Measured — the axe census shows the doubled alt on every teaser instance
(`"The glass atrium…" | "The glass atrium…"`), and `picture-teaser` renders two
visible images stacked.

`Media.css` states the dependency plainly ("visibility is controlled by the
consuming component") and **the TagHelper exposes `teaser` as a public preset
anyway**, with the source's own `_Components.cshtml` using it standalone at line
258. So `preset="teaser"` has an undeclared dependency on the consumer's
stylesheet, and using it as documented produces a duplicated image and a
duplicated announcement.

axe does not flag it: two images with correct alt text are two correct images.

**Decision:** reproduced. **Open question:** either `teaser` should be documented
as Teaser-internal and removed from `app-picture`'s accepted presets, or
`Media.css` should carry a default (`HorizontalSources { display: none }`) so the
standalone case degrades to one image instead of two.

## The class-name parameterisation is a styling switch, and it is where each step got interesting

### F-NEW · `.Media` names the figure for one caller and the picture for the other

**Surface:** `BuildFigureHtml(figureClass, pictureClass)` and its two callers.
Found by reading `TeaserTagHelper`, not `PictureTagHelper`.

`BuildFigureHtml` has two class-name parameters that look like dead extension
points and are not:

| Caller | figure class | picture class |
|---|---|---|
| `PictureTagHelper` | `Media` (default) | `Media-picture` (default) |
| `TeaserTagHelper` | `MediaContainer` | **`Media`** |

So `.Media` is the **figure** on one path and the **picture** on the other, and
`Media.css`'s img rules — scoped to `.Media-picture` — **do not apply to a Teaser
at all.** Measured on the route with the Teaser parameterisation:
`display: inline` on the picture (the `<picture>` default; `Media.css`'s
`display: block` never matched) and no `width`/`height`/`object-fit` on the img.

This shaped every step:

- **Step 1** reproduced it and measured it.
- **Step 2** could not put a border on `:where(.Media)` — that would border a
  Teaser's `<picture>`. The selector became `:where(figure.Media)`, which states
  the intent the file's existing comment already claimed ("figure reset") and
  keeps specificity at zero. The original `margin: 0` gets away with the
  ambiguity only because a stray `margin: 0` on a `<picture>` is harmless.
- **Step 3** could not express the contingency at all. See below.

---

### F-NEW · A utility cannot be contingent on the caller's class name, so two CSS selectors became two string comparisons

**Surface:** step 3, `pictureUtilities.ts`. **The step-3 finding, and a different
one from Button's.**

Step 2's two rules were both contingent on a name the *caller* chooses:

```css
:where(figure.Media)   { …card treatment… }
:where(.Media-picture) { display: block; & img { …sizing… } }
```

That contingency is the mechanism by which one builder serves two visual
contracts — the consumer supplies its own. A utility class on an element is
unconditional by construction, so emitting `rounded-lg border border-hairline`
on the figure would give a Teaser a card border the stylesheet deliberately
withheld. The condition had to move into JavaScript:

```ts
figureClass === "Media" ? FIGURE_CARD : FIGURE_RESET
```

**This is the Button port's "resolve it in JS, never emit both" lesson arriving
by a genuinely different route.** There the problem was two utilities at equal
specificity and Tailwind's sort order deciding. Here there is no conflict at all
— only a *condition* that CSS could state and the utility layer cannot express.
The generalisation is broader than the Button finding: **any selector whose match
depends on a value the component receives as a prop becomes a pre-render decision
in JS**, whether or not two declarations compete.

**And it closes the switch.** Under CSS any caller could pass a third class name
and get a documented, predictable answer from the cascade: no match, no styling.
After step 3 the switch is a pair of string equality tests against the two names
`pictureUtilities.ts` knows about, so a third caller silently gets the Teaser
branch. **The stylesheet was extensible by construction; the component is
extensible only by editing it.** Same shape as F-062's loss of the
custom-property override seam, reached through selector *matching* rather than
custom-property *filling* — which suggests F-062 is the specific case of a
general rule rather than a quirk of gate-based stylesheets.

`Media.css` is now comments only, as `Card.css` was. Kept, because the record of
what the source said outlives eleven declarations.

### F-NEW · Tailwind's preflight hides a source overflow bug that the Razor app has

**Surface:** Tailwind v4 preflight vs `Media.css` + `Teaser.css`.

Preflight ships `img,video{max-width:100%;height:auto}` and
`img,svg,video,…{display:block}` (verified in the generated chunk).

Two consequences:

1. **`Media.css`'s `img { display: block }` is redundant in our substrate** and
   was already shadowed before step 3. Component CSS is unlayered and beats
   `@layer base`, so the verbatim rule did win — but it was winning a race
   against an identical value.
2. **The port has an overflow guard the source does not.** On the Teaser call
   path `Media.css` gives the img no `max-width` at all, so an 800 px `stacked`
   crop inside a 240 px card would render at intrinsic width and overflow. Here
   preflight clamps it to 240 px and it looks correct. Measured: img box 240 px
   with `max-width: 100%` from preflight, in a demo where no component rule
   applies to the img.

Following the mechanism into `Teaser.css` predicts a live source bug:
`@container (max-width: 24.999rem)` (State A, flow-vertical) sets
`.Media.StackedSources { display: block }` and declares **no img rules**, while
`Media.css`'s img rules are scoped to `.Media-picture` which a Teaser never uses.
The only img sizing in that state comes from the `@supports not
(container-type)` fallback, which does not apply in a browser that supports
container queries. So a narrow Teaser in a modern browser has an unbounded img —
a WCAG 1.4.10 reflow failure at exactly the container width the layout is
designed for.

**Stated as an inference, not a measurement.** I verified the mechanism (the img
rules do not apply on the Teaser path, and an unclamped img renders at intrinsic
width) but not the outcome in the Razor app, because `Teaser.css` is not ported.
It is cheap to check upstream and worth checking.

**Positive finding worth naming:** our reflow gate is green partly because of the
substrate, not only because of the port. `picture-reflow.cjs` reports
intrinsic-vs-box per image for that reason — so a future change that removes
preflight's clamp surfaces as an image measurement rather than as a mysterious
page-level overflow.

## Smaller findings, each of which cost something

### F-NEW · The one primitive stylesheet that needed no repair, and read no tokens at all

**Surface:** `Media.css`, step 1.

Two firsts for this set, both worth recording because they are the exception:

- **It compiled byte-identical.** `sha1 b7f3d8ec885ff0aa53e8685300e31a7f9963c138`,
  18 lines, 415 bytes, `diff` clean, straight through Lightning CSS. Every other
  primitive stylesheet so far needed a repair — `Button.css`'s bare `var()` was a
  hard build error (F-061's sibling finding).
- **It reads zero design tokens, of either tier.** F-061's prescribed check,
  `grep -o '\-\-COLOR-[A-Z0-9]*' Media.css`, returns nothing — and so does a
  search for lowercase semantics. `primitive-tokens.css` had nothing to bridge,
  so F-061's failure mode (a silently colourless component) could not arise.

**The useful qualification to F-061's advice:** the grep is necessary and not
sufficient. An empty result has two very different meanings — "reads the semantic
tier, bridge covers it" and "reads no tokens at all, so step 1 is the source's
own appearance and step 2 is doing all the work". Here it was the second. Step 1
looked exactly like the source, and that was honest rather than lucky, but it
also meant the bridge contributed nothing and every design decision was deferred
to step 2. Worth distinguishing, because the two cases imply very different
amounts of remaining work.

### F-NEW · The source encodes the alt text and not the URLs interpolated into `srcset`

**Surface:** `MediaHelper.BuildFigureHtml` / `RenderPictureGroup`.

The source builds HTML by string concatenation and calls
`HtmlEncoder.Default.Encode` on exactly one value:

```csharp
var encodedAlt = HtmlEncoder.Default.Encode(altText);
...
sb.Append($"<source ... srcset=\"{BuildSrcset(source, image, "avif")}\" ...>");
```

`sizes` and `media` come from the hard-coded preset table and are safe. The crop
URLs do not: they come from `GetCropUrl`, which derives from the media item's
path — an **editor-controlled filename**. A filename containing a double quote
terminates the attribute. Low severity (media library upload, and Umbraco
sanitises filenames) but it is an unencoded CMS value interpolated into an HTML
attribute, and the same function encodes the one right next to it.

**The React port deletes the whole class of bug for free**, which is the point
worth recording: JSX escapes every interpolated value, so `HtmlEncoder` is not
merely unnecessary here, it would double-encode. **A hand-rolled string builder
has to be right about escaping at every single interpolation; a JSX tree is right
by construction.** That is a real, unglamorous advantage of the port over the
source, and it is invisible in a diff of the rendered output.

### F-NEW · `GetCropUrl(...) ?? ""` yields `src=""`, which re-requests the current page

**Surface:** `MediaHelper.CropUrl`.

`image.GetCropUrl(...) ?? ""` — when Umbraco cannot resolve a crop, the fallback
is the empty string. `src=""` is not a no-op: it resolves to the document's own
URL, so the browser re-requests the current page and tries to decode HTML as an
image. On a hero that is an extra full page load.

Reproduced verbatim (`umbracoCropUrl` returns `""` for an empty media URL, pinned
in the tests). **Upstream fix:** omit the `<source>`/`<img>` entirely when the
crop does not resolve, which is what the TagHelper's own `SuppressOutput()`
branch already does for a missing image — the two failure modes are treated
inconsistently one function apart.

### F-NEW · One media query anywhere in a group disables resolution switching for the whole group

**Surface:** `RenderPictureGroup`'s `isArtDirection`.

```csharp
var isArtDirection = group.Sources.Any(s => s.Media != null);
```

**Any** source carrying a media query switches the whole group's `<img>` from
`srcset`+`sizes` to a bare `src`. Correct for both existing presets, and a trap
for the third: a group mixing one media-scoped source with unscoped ones silently
loses resolution switching on the fallback `<img>`, *and* the unscoped source
matches at every viewport and beats the scoped one only by document order. The
mode becomes neither one thing nor the other.

Pinned in `mediaHelper.test.ts` with a synthetic mixed group, because no preset
exercises it today and the next one might.

Related and also pinned: the fallback `<img>`'s `src` is
`lastSource.Widths[0]` — the **narrowest** width of the **last** source. For
`hero` that is `wide` @1280: the widest crop's smallest step. Not the narrowest
crop, not the widest width. Easy to "tidy" wrongly.

### F-NEW · `hero`'s three ascending `max-width` queries only work in the order they are written

**Surface:** `Presets["hero"]`.

`(max-width: 21.24999rem)`, `(max-width: 48rem)`, `(max-width: 64rem)`,
`(min-width: 64rem)`. `<source>` is first-match-wins, so a wider `max-width`
placed first would swallow every narrower one and every viewport below 64rem
would take the same crop. Reordering the table is a total, silent regression.

Measured boundaries, exact (`picture-negotiate.cjs`, either side of each):

| viewport | crop chosen |
|---|---|
| 320, 339 px | `mobile` (4:5) |
| 341, 767 px | `portrait` (3:4) |
| 769, 1023 px | `mid` (16:9) |
| 1025, 1440 px | `wide` (21:9) |

Pinned as an ordering assertion rather than a value assertion, so the test fails
on a reorder rather than only on an edit.

**Positive finding:** art direction works exactly as specified, and AVIF was
selected at every viewport — 9 media files fetched on a full page load, all
`.avif`, no webp and no jpg. The three-format ladder resolves to one request.

## Two ways I nearly reported something false

### F-NEW · A snapshot key that contains the thing under test cannot detect a change to it

**Surface:** `picture-computed.cjs`, step 3. **Caught by reading the output, not
by the exit code.**

The first version keyed each instance on `data-id` plus the figure's and
picture's full `className`. Step 3 adds utility classes to both, so the diff
reported:

```
23 picture instance(s) measured. 0 diff(s), 46 gone, 46 new.
```

**Zero property diffs because nothing matched.** Every one of the 46 keys
changed, so not a single property was ever compared. The headline number was
exactly what a clean conversion produces, and it was vacuous. The `46 gone, 46
new` line is the only thing that gave it away, and a probe that reported just the
diff count would have been silently useless.

Re-keyed on structural identity only — `data-id` plus an **allow-list** of the
source's own class lexicon (`Media`, `Media-picture`, `MediaContainer`,
`StackedSources`, `HorizontalSources`, `grid-container-full`, `demo-extra-class`),
so a new utility can never re-key an instance and a renamed structural class
always does. Then re-baselined properly: parked the step-3 files, rebuilt at step
2, re-measured, restored, rebuilt, diffed.

**Real result: 0 diffs, 0 gone, 0 new**, across 23 instances × 2 appearances ×
figure/picture/img computed styles plus the `srcset`/`sizes`/`loading`/`width`/
`height` attributes.

**The transferable rule:** an allow-list, not a pattern. The Button port avoided
this by keying on `data-*` axes; a component whose identity lives in class names
has no such luxury and needs the exclusion stated explicitly.

Worth noting the probe deliberately snapshots the `srcset`/`sizes`/`loading`
**attributes** as well as computed style. They are not style, they are this
component's entire contract, and no other instrument in the project observes
them — a preset-table refactor would otherwise pass every gate.

### F-NEW · `w-full` inside a shrink-to-fit flex item is circular, and it faked a 170 px component defect

**Surface:** `Picture.kitchensink.tsx`, step 2.

After step 2 the reserved-height probe reported 22 pictures at 0 px unreserved
and one — `picture-live`, the cell explicitly labelled "the CLS target" — at
**+170 px**. It read exactly like a residual component defect in the worst
possible place.

It was the harness. `Block` lays its children out with `flex flex-wrap`, so a
child is a shrink-to-fit flex item whose width is decided by its **content**;
`w-full` then resolves against a width its own content produced. Measured: with
images blocked the alt text sized the track to **373 px**, with them loaded the
images sized it to **770 px**, and the probe read the difference as unreserved
height. Every other cell had a definite width and was immune.

Fixed with `w-[48rem] max-w-full`. Result: 0 px unreserved on all 23.

**Related to `Cell`'s `min-w-0` note (F-024) and the opposite mistake.** F-024
warns that a *fixed* width inside a flex item sizes its track and breaks
`max-w-full`. This is the dual: a *percentage* width inside an auto-sized track
has nothing stable to resolve against. `min-w-0` does not help, because the
problem is `flex-basis: auto` on the ancestor, not the minimum.

### F-NEW · `next start` reads the build manifest once, so a concurrent rebuild serves HTML pointing at a deleted CSS chunk

**Surface:** the whole measurement effort. **Cost two full rounds of
measurements and produced one wrong conclusion before it was caught.**

CLAUDE.md warns about `pkill -f "next start"` not matching `next-server`, and
about `curl` 200 proving only that something is listening. This is a **third
variant it does not name**, and the guidance it does give is insufficient against
it:

Several agents port in parallel against one `.next`. `next start` reads the build
manifest into memory at boot. When another agent runs `npm run build`, the
running server keeps serving HTML that references the *previous* build's Tailwind
chunk — a filename that no longer exists on disk. Measured:

```
$ curl -s .../primitives/picture | grep -o 'chunks/[^"]*\.css'
chunks/0ovk_18rf_3r3.css     <- 404, not on disk
chunks/1y5x5g5lz-5vs.css     <- 143 bytes: Media.css only
```

The route returned **200**, rendered, and loaded **only the component's own
stylesheet** with the entire design system absent. Every width utility inert,
`max-width: none`, the hero at 1424 px instead of 832 px. I read those numbers as
component behaviour and started reasoning about them.

**Neither documented check catches it.** `curl` returns 200. The log says
`Ready in 56ms` — and the server *was* ready; the build moved afterwards. Killing
by port and restarting fixes it only until the next rebuild, which during this
port happened three times inside twenty minutes.

**Two fixes, and both were needed.**

1. **`picture-guard.cjs`, required by every probe.** Asserts before measuring
   that every linked stylesheet has a non-null `.sheet`, that `--color-canvas`
   and `--color-hairline` resolve, that `<main>`'s `max-width` is not `none`, and
   that `body` has a background. It caught the stale build twice more after being
   written, including once mid-run in `picture-cls.cjs`.
   It also had to **poll rather than assert once**: the first version fired a
   false "stale build" on the slow-4g condition, where the 55 KB chunk genuinely
   takes over a second — the guard's own failure mode, in the same shape as the
   bug it exists to catch. A guard that cannot tell "not yet" from "never"
   discredits itself.
2. **A private, immutable substrate**, because a guard that only *detects* the
   race still loses it on a four-minute probe. `rsync` the freshly built `.next`
   into a scratchpad directory whose own `next.config.ts` sets `distDir` to it,
   with `node_modules` and `public` symlinked back, and `next start` there on a
   private port. Immune to any rebuild, and it does not require editing
   `web/next.config.ts` (which is off-limits, and did not need changing).

**Recommendation for CLAUDE.md:** the existing rule is "kill by port and read the
log for `Ready in`". That is necessary and not sufficient under parallel agents.
The rule should be **"assert the page is styled in the probe itself"** — a `curl`
200, a `Ready in`, and a rendering page are all consistent with a totally
unstyled route.

## Summary for the project owner

**The `next/image` question is settled, not deferred.** `MediaHelper` is
substantial and three of its guarantees — HTML art direction over named crops,
container-query source selection, and focal-point crops — have no expression in
`next/image`. The two escape hatches each remove the reason to use it, and
`images.remotePatterns` cannot be configured for a CMS host that is unknown at
port time. Next's own `no-img-element` lint rule exempts `<img>` inside
`<picture>`, which is the framework conceding the same point. **`web/next.config.ts`
needs no change.**

**The one thing `next/image` gets right was adopted without it.** Required
dimensions. Step 1 measured CLS 0.253 (POOR) and 3998 px of unreserved height;
step 2 fixed it with `width`/`height` on each `<source>` — which is *more* than
`next/image` can express, because the crop changes per breakpoint. Upstream this
needs no new CMS data and is the port's principal recommendation.

**The most valuable available change is an accessibility one, and it needs your
decision.** `Alt ?? ""` makes a forgotten alt indistinguishable from a deliberate
`alt=""`; axe passes both and the atomica11y criteria cannot separate them. A
TypeScript discriminated union would make the intent mandatory at zero runtime
cost — a strict improvement over the source — but it is an API change.

**Two false greens are recorded in as much detail as the real findings**, because
each was one step away from a confident wrong answer: CLS 0.000 on three of four
network conditions, and a computed-style diff reporting 0 diffs because its key
contained the thing under test.
